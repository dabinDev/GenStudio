# 塞隆studio Operations README

## Production Domain

Use `https://studio.cylonai.cn` for the 塞隆studio frontend and backend origin. Official-site SSO should redirect users to:

```text
https://studio.cylonai.cn/auth/callback?code=xxx
```

The `code` is not manually entered in production. The backend exchanges it through `OFFICIAL_AUTH_EXCHANGE_URL`, writes the `genstudio_session` HttpOnly cookie, then redirects back to the frontend hash route.

## Required Environment

Start from `server/.env.production.example` and set real values:

- `GENSTUDIO_ENV=production`
- `GENSTUDIO_SECRET_KEY`: long random value, backed up securely. This key protects sessions and encrypted API keys.
- `GENSTUDIO_COOKIE_SECURE=true`
- `GENSTUDIO_ENABLE_DEV_LOGIN=false`
- `GENSTUDIO_AUTO_CREATE_TABLES=false`
- `GENSTUDIO_CORS_ORIGINS=https://studio.cylonai.cn`
- `GENSTUDIO_ADMIN_IDENTIFIERS`: comma-separated non-email admin identifiers, such as a local username.
- `OFFICIAL_AUTH_EXCHANGE_URL`, `OFFICIAL_AUTH_CLIENT_ID`, `OFFICIAL_AUTH_CLIENT_SECRET`
- `DATABASE_URL` for the production MySQL database `genstudio`
- `OBJECT_STORAGE_ENABLED=true`
- `OBJECT_STORAGE_ENDPOINT_URL`, `OBJECT_STORAGE_BUCKET`, `OBJECT_STORAGE_ACCESS_KEY_ID`, `OBJECT_STORAGE_SECRET_ACCESS_KEY`
- `OBJECT_STORAGE_PUBLIC_BASE_URL`, the CDN/public base URL for uploaded reference assets

The app refuses to start in production when these safety checks are not met.

## Database Migration

Production must not rely on startup auto-create. Apply the initial schema before first deploy:

```bash
mysql -h <host> -u genstudio -p genstudio < server/migrations/001_initial_schema.sql
```

For later schema changes, add a new numbered SQL file under `server/migrations/` and apply it during maintenance. Keep backups before every migration.

## Backup

Back up at least these tables: `users`, `user_credentials`, `sessions`, `api_keys`, `models`, `sub_models`, `conversations`, `conversation_messages`, `generated_assets`, `call_logs`.

Example:

```bash
mysqldump -h <host> -u genstudio -p --single-transaction --routines --triggers genstudio > genstudio-$(date +%F-%H%M).sql
```

Store `GENSTUDIO_SECRET_KEY` with the backup set. Without it, encrypted user API keys cannot be decrypted after restore.

## Health Checks

Use:

```text
GET /api/health
```

Expected production result:

```json
{"status":"ok","database":"ok","storage":"configured"}
```

If storage is `not_configured`, uploads may still fall back during development, but production startup will be rejected.

## Upload Storage

Production uploads use an S3-compatible `PUT` presigned URL generated by 塞隆studio. Configure the storage endpoint, bucket, region, access key, secret key, optional object key prefix, and public CDN/base URL through the `OBJECT_STORAGE_*` variables. Development without object storage can still use the legacy provider `/api/upload/presign` compatibility path, but production requires first-party object storage so reference images and videos are not stored as local data URLs.

## R2 Asset Lifecycle

Apply `server/migrations/009_asset_storage_lifecycle.sql` before starting a release that contains the R2 lifecycle worker. The migration is additive: it extends `generated_assets` with local/R2 state, checksum, size, retry, expiry, and scheduling fields. Do not drop these columns during an application rollback.

Required object storage configuration:

- `OBJECT_STORAGE_ENABLED=true`
- `OBJECT_STORAGE_ENDPOINT_URL`: the Cloudflare R2 S3-compatible endpoint
- `OBJECT_STORAGE_REGION=auto`
- `OBJECT_STORAGE_BUCKET`: the exact production bucket
- `OBJECT_STORAGE_ACCESS_KEY_ID` and `OBJECT_STORAGE_SECRET_ACCESS_KEY`: read/write credentials supplied only through the production environment
- `OBJECT_STORAGE_KEY_PREFIX`: defaults to `genstudio`
- `OBJECT_STORAGE_PUBLIC_BASE_URL`: HTTPS public/CDN base URL that can serve both originals and thumbnails

Generated objects use UTC dates and stable asset IDs:

```text
<prefix>/assets/YYYY/MM/DD/<asset-id>/original.<ext>
<prefix>/assets/YYYY/MM/DD/<asset-id>/thumbnail.webp
```

Thumbnails are WebP images with a maximum side of 640 pixels, quality 78, and no upscaling. The worker uploads the original first, then the thumbnail, and verifies both objects with `HEAD` before marking the asset `r2_synced`.

Delivery and retention rules:

- New assets are available from their managed local file immediately.
- Local originals and thumbnails are retained for exactly 24 hours from asset creation.
- Before 24 hours, authenticated conversation delivery prefers the local content/thumbnail routes.
- At and after 24 hours, a verified `r2_synced` asset serializes only its R2 original and thumbnail URLs; the worker removes its local files.
- `local_pending`, `remote_pending`, `syncing`, and `sync_failed` assets retain any available local copy. The orphan cleanup job must not delete a tracked file without a verified R2 original and thumbnail.
- A failed synchronization never changes the original external URL and never deletes the only surviving copy.

The worker defaults to a 60-second interval and a batch size of 8. Owners can change the interval (15-3600 seconds), batch size (1-100), and automatic-sync switch under Admin -> System Settings -> Image Storage and Synchronization. The 24-hour TTL is fixed and cannot be changed in the admin UI.

Admin inspection and recovery endpoints:

```text
GET  /api/admin/asset-sync/settings
PUT  /api/admin/asset-sync/settings
GET  /api/admin/asset-sync/preview
POST /api/admin/asset-sync/run
POST /api/admin/asset-sync/retry-failed
```

`settings:view` can inspect counts, bytes, eligible rows, last manual/automatic runs, and recent failures. Only `maintenance:asset_cleanup` can change settings, run synchronization, or reset failed rows. Every mutation writes an admin audit log. API responses do not expose local paths, object keys, credentials, or full storage errors outside the bounded failure message.

Recovery sequence for failed assets:

1. Confirm `/api/health` reports `storage: configured` and inspect the failure table without changing state.
2. Correct endpoint, bucket, public-base, DNS, or R2 permission problems in the deployment environment.
3. Use `Retry Failed` to reset failed rows to a local or remote pending state.
4. Use `Sync Now` and verify that failure count decreases and `r2_synced` increases.
5. Confirm both the original and thumbnail public URLs return successful raster responses before allowing the 24-hour cleanup boundary to pass.

Isolated object-store verification must use a unique prefix such as `genstudio/test/<uuid>/`. Upload one small raster original and one WebP thumbnail through the configured object client, `HEAD` both, read both through `OBJECT_STORAGE_PUBLIC_BASE_URL`, and delete exactly those two keys. Never list or delete a broad bucket prefix, and never print credentials or signed headers. A release is blocked if upload, `HEAD`, public read, or exact-key deletion fails.

Rollback sequence:

1. Disable automatic synchronization in the admin console if the current application is still reachable.
2. Restore the previous server and static artifacts, then restart the API and validate health.
3. Keep migration 009 columns and R2 objects in place; an older application can ignore the additive columns.
4. Do not delete local assets or R2 objects during rollback. Resume or retry synchronization only after the corrected release is running.
5. Restore the database backup only when migration or data integrity is the root cause and the backup has already been validated.

## Reverse Proxy

Nginx minimum shape:

```nginx
server {
  listen 443 ssl http2;
  server_name studio.cylonai.cn;

  client_max_body_size 80m;

  location /api/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
  }

  location /auth/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
  }

  location /admin/ {
    alias /opt/nginx/html/genstudio-admin/;
    try_files $uri $uri/ /admin/index.html;
  }

  location / {
    root /opt/nginx/html/genstudio;
    try_files $uri $uri/ /index.html;
  }
}
```

## Rate Limits

The app includes an in-process limiter for login, registration, model list/test, generation, video query, and upload-presign routes. For multiple backend instances, mirror these limits at the gateway or move to Redis-backed limiting.

## Long Video Jobs

The current backend persists submitted video task messages in conversations and stores failed query records with retry enabled. For high traffic production, move video creation/query to a queue and worker model so jobs survive deploys and client disconnects.

## Deployment Runbook

2026-06-10 verified production release flow for `studio.cylonai.cn`:

- Production host: Guangzhou CVM `175.178.189.234`.

- Backend container: `genstudio-api`, mapped as `127.0.0.1:18082 -> 8000`.

- Remote deploy helper: `deploy/remote-brand-deploy.sh`.
- The helper refuses to reload Nginx if `/admin/` routing is missing; install the Nginx shape above before publishing the independent admin app.

Canonical release order:

1. Review `git status --short` and confirm only intended source/documentation files are modified.
2. Run the relevant frontend/admin tests for the changed areas.
3. Build `fronted/dist` and `admin/dist` from a clean local working tree.
4. Package only `server/`, `docs/`, `.dockerignore`, `fronted/dist`, `admin/dist`, and optional `RELEASE_VERSION` into `.deploy-stage/genstudio-brand-release.tar.gz`.
5. Upload the release package and `deploy/remote-brand-deploy.sh` to the Guangzhou host.
6. Run the remote helper, which backs up current server/static files before replacing them.
7. Verify backend health, Nginx config, frontend route, and admin route.
8. Commit and push the source changes after verification, or commit before deployment when a traceable release SHA is required. Do not commit `.deploy-stage`, `dist`, screenshots, logs, or secret files.

## Rollback

The remote helper stores timestamped backups under `/opt/genstudio_backups` before replacing files.

Rollback order:

1. Identify the latest good backup directories:
   - `/opt/genstudio_backups/server-<timestamp>`
   - `/opt/genstudio_backups/fronted-<timestamp>`
   - `/opt/genstudio_backups/admin-<timestamp>`
2. Restore application/static files with `rsync --delete` back to `/opt/genstudio/server`, `/opt/nginx/html/genstudio`, and `/opt/nginx/html/genstudio-admin`.
3. Rebuild and restart `genstudio-api` if the backend was restored.
4. Run `docker exec nginx nginx -t && docker exec nginx nginx -s reload`.
5. Verify `http://127.0.0.1:18082/api/health`, `https://studio.cylonai.cn/`, and `https://studio.cylonai.cn/admin/`.

Roll back database only from a tested backup when a migration itself is the fault; otherwise prefer a forward fix.
