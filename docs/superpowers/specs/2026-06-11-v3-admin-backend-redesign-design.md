# v3-admin-vite 独立管理后台重写设计

## 背景

当前管理后台嵌在创作主站 `fronted/src/App.vue` 的 `#/admin` 页面里，已经承担了模型、公用模型、提示语、用户、积分、创作记录、审计日志等复杂管理能力。继续在主站内部堆叠后台页面，会让样式、路由、状态和权限边界越来越混乱。

本次重写采用独立后台方案：创作主站继续使用当前项目，管理后台新增独立 `admin/` 前端工程，并参考 `v3-admin-vite` 的 Vue3 中后台架构和交互模式重写。

## 目标

- 保留当前创作主站功能和整体技术结构。
- 新增独立管理后台工程，访问路径为 `/admin/`。
- 删除旧的 `#/admin` 内嵌后台页面，不再维护旧后台 UI。
- 前台、后台共用同一套用户体系、登录态、授权登录、CSRF 和管理员权限。
- 管理后台使用标准中后台信息架构：侧边菜单、顶部栏、面包屑、搜索表单、数据表格、详情抽屉、确认弹窗、图表看板。
- 后台接口继续复用现有 FastAPI `/api/admin/*` 能力，后端作为权限最终兜底。

## 非目标

- 不把创作主站迁移到 `v3-admin-vite`。
- 不直接整包替换为第三方模板业务代码。
- 不新增第二套后台账号系统。
- 不改变现有模型调用、图片生成、视频生成、对话等用户侧业务逻辑。
- 不在这次设计中重写后端业务服务，只补齐后台需要的少量管理接口和字段。

## 后端能力盘点与保留边界

后台重写前必须以现有后端能力作为功能基线。新后台可以新增接口、增强统计、细化权限，但不能删除或弱化以下能力。

### 身份、会话和授权

现有能力：

- 本地注册、密码登录、登出。
- 官方授权登录回调。
- 开发登录。
- `genstudio_session` 服务端 session。
- `SessionCsrfToken` 写操作 CSRF 防护。
- 用户状态：`active`、`disabled`、`deleted`。
- 管理员判断：管理员邮箱和管理员标识配置。

必须保留：

- 前台和后台共用同一套用户、session、CSRF 和授权登录。
- 禁用或删除用户后，前台和后台都不能继续使用。
- 后台不可绕过 `require_admin_user`。

需要增强：

- 管理员权限从单一 `isAdmin` 扩展为可表达的权限点，但不破坏现有管理员邮箱配置。
- 登录、权限、CSRF、账号状态相关中文错误提示必须统一修复乱码。
- 后台需要能看到用户最近 session、最近活跃时间、登录来源摘要。

### 模型、Catalog 和公用模型

现有能力：

- 用户模型分组 `ModelGroup`。
- 子模型 `SubModel`。
- API Key 加密存储。
- Catalog 模型、参数、选项、渠道分组。
- KK catalog 同步。
- catalog 自动关联模型名。
- 公用模型发布、取消发布。
- 公用模型展示名、描述、输入 hint、图标、标签、默认参数。
- 公用模型可被普通用户使用，但普通用户不可编辑公用模型。
- 私有模型归属于用户，私有模型不扣平台积分。

必须保留：

- 所有模型字段、catalog 参数和默认参数都要能在新后台查看和编辑。
- 前台选择模型时仍能按 catalog 展示支持的参数。
- 公用模型仍使用管理员配置的 Base URL、API Key 和模型信息。
- 普通用户不能删除或编辑公用模型。

需要增强：

- 模型列表要展示健康状态、最近测试时间、最近调用、失败率、超时率、平均响应时长。
- 模型参数要结构化展示：长度、比例、分辨率、图片数量、参考图数量、音频、seed、quality 等。
- 模型批量测试结果需要持久化，用于“移除不可用”和运营统计。
- 模型权限要区分：查看、编辑、发布公用、取消公用、删除、批量测试、配置积分价格、查看密钥摘要。

### 创作代理、任务轮询和资产

现有能力：

- 文案代理 `/api/proxy/text` 和 `/api/proxy/text/query`。
- 图片代理 `/api/proxy/image` 和 `/api/proxy/image/query`。
- 视频代理 `/api/proxy/video/create` 和 `/api/proxy/video/query`。
- 上传、本地资产、对象存储预签名上传。
- 长耗时任务处理和轮询。
- 图片、视频、文案消息写入会话。
- `GeneratedAsset` 保存图片、视频资产。
- 对上游错误做用户可读转换。
- 失败时积分自动退款。

必须保留：

- 文案、图片、视频生成流程不可因后台重写发生退化。
- 轮询任务、成功资产、失败原因和退款状态都要继续写入数据库。
- 管理后台查看创作记录时必须能看到用户输入、参考图、模型响应、结果图/视频、任务 ID、错误信息和原始 JSON。

需要增强：

- 后台记录页要能按任务状态、耗时、超时、上游错误类型、是否退款筛选。
- 任务状态时间线要展示：创建、提交上游、处理中、查询次数、完成、失败、退款或扣费确认。
- 上游系统级错误不直接暴露技术细节给用户端，但后台详情里要保留脱敏后的 raw 信息用于排查。

### 会话、历史记录和调用日志

现有能力：

- 会话列表、创建、详情、重命名。
- 用户消息、AI 消息、状态、错误、请求 JSON、响应 JSON。
- 资产挂到消息上。
- `CallLog` 记录能力类型、接口、状态、耗时、提示摘要、错误、usage、请求参数、响应摘要、会话 ID、消息 ID、公用模型标记。
- 用户侧调用日志和调用摘要。

必须保留：

- 所有创作返回结果要同步进入历史会话。
- 后台记录不能只看 call log，也要能关联 conversation message 和 generated assets。
- 对话重命名、历史查看和资产加载不能被旧后台删除影响。

需要增强：

- 调用日志要成为运营图表主数据源。
- 后台需要按用户、模型、能力、状态、时间、是否公用模型统计。
- 需要补齐队列耗时、上游耗时、轮询次数、任务总耗时等更细字段；现有无法直接获取的字段先从 request/response summary 解析，后续再持久化。

### 积分、计费和流水

现有能力：

- 用户积分账户。
- 积分流水。
- 默认能力价格：文案、图片、视频。
- 模型级价格覆盖。
- 新用户注册送积分配置。
- 管理员充值和扣减。
- 生成任务预扣、成功确认、失败退款。
- 私有模型不扣积分，公用模型按配置扣积分。

必须保留：

- 私有模型不扣积分。
- 公用模型按后台配置扣积分。
- 失败自动退款。
- 积分流水必须可追踪到用户、能力、模型、会话、消息、任务。

需要增强：

- 后台要展示余额、冻结积分、总充值、总消费、总退款。
- 运营图表要展示积分消耗趋势、退款趋势、按模型消耗、按用户消耗。
- 管理员调整积分必须填写原因并进入审计日志。

### 审计、系统设置和维护

现有能力：

- 管理员操作日志。
- 系统设置表。
- 用户重复账号合并维护能力。
- 生产安全配置校验。

必须保留：

- 高风险后台操作必须写审计日志。
- 系统设置不能散落到前端硬编码。
- 用户去重/合并能力后续可以后台化，但必须保留数据迁移逻辑。

需要增强：

- 审计日志要增加风险等级、目标对象、操作者、结果、摘要。
- 系统设置要后台化：注册送积分、上传限制、任务轮询、站点品牌、模型默认策略。
- 用户合并要做成管理员高级工具，并要求二次确认。

## 新后台后端增强原则

- **不删功能**：任何已有用户侧接口、管理接口、表字段和业务流程都不能因为后台重写被删除。
- **可加接口**：为了更精细的图表、权限和记录详情，可以新增 `/api/admin/*` 接口。
- **后端兜底**：权限、积分、模型可见性、危险操作确认结果都必须由后端校验。
- **前端轻编排**：后台前端负责展示和操作编排，不把权限和业务规则写死在页面里。
- **数据可追溯**：每一次管理操作、积分变化、生成任务、上游失败都要能从后台追到相关用户、模型、会话、消息和任务。

## 项目结构

```text
E:\FlutterProject\GenStudio
├─ fronted/     创作主站，继续承载文案、图片、视频、设置、个人中心
├─ admin/       新管理后台，基于 v3-admin-vite 风格重写
├─ server/      现有 FastAPI 后端，继续提供 /api 和 /api/admin
└─ deploy/      Docker、Nginx、SSL、发布配置
```

## 访问与部署

- `/` 指向 `fronted/dist`。
- `/admin/` 指向 `admin/dist`。
- `/api/*` 继续反向代理到 FastAPI。
- 旧的 `/#/admin` 从主站路由中删除。主站不再渲染管理后台，也不保留旧后台跳转壳。
- 生产环境 Nginx 需要给 `/admin/` 增加 history fallback，刷新后台深层路由时仍返回 `admin/dist/index.html`。

## 统一用户与登录体系

前台和后台必须共用同一套身份系统：

- 同一张 `users` 表。
- 同一个 `genstudio_session` cookie。
- 同一组 `/api/auth/*` 接口。
- 同一个 `isAdmin` / `require_admin_user` 权限判断。
- 同一套官方授权登录、本地账号登录、注册、登出流程。
- 同一套 `/api/auth/csrf` 和 `X-CSRF-Token` 写操作保护。

后台启动流程：

1. 请求 `/api/auth/me`。
2. 未登录时跳转到主站登录页，并携带 `redirect=/admin/`。
3. 已登录但不是管理员时显示无权限页。
4. 已登录且是管理员时加载后台菜单和数据。
5. 后台写操作先确保已有 CSRF token，没有则请求 `/api/auth/csrf`。

后端兜底：

- 所有 `/api/admin/*` 接口继续依赖 `require_admin_user`。
- 前端隐藏菜单只作为体验优化，不能作为安全边界。
- 用户禁用、删除、会话失效时，后台应统一跳出或展示明确状态。

需要同步修正：

- 共享认证模块里的中文错误提示存在乱码，后台重写时应修复为 UTF-8 中文文案，避免登录、权限、CSRF 提示继续出现乱码。

## 后台整体布局

后台使用典型管理系统布局：

- 左侧固定菜单：展示一级模块和二级页面。
- 顶部栏：站点名、折叠菜单、面包屑、主题切换、当前管理员、退出登录。
- 主内容区：页面标题、摘要指标、搜索区、列表区、详情抽屉。
- 详情抽屉：用户详情、模型详情、记录详情、审计详情等统一在右侧展示。
- 危险操作：删除、禁用、扣减积分、取消公用等必须弹窗确认。

视觉原则：

- 以白色后台为默认模式，深色模式可用但不是主表达。
- 避免大面积紫色和低对比渐变。
- 列表页使用紧凑、清晰、可扫描的企业后台风格。
- 一个表格行内不放超过两个直接按钮，更多操作进入“操作”下拉或右侧抽屉。

## 权限模型设计

初始实现仍以管理员邮箱和管理员标识作为超级管理员来源，但后台内部要按权限点组织，避免所有功能都写成一个粗糙的 `isAdmin` 分支。

### 角色

- `super_admin`：主管理员。拥有全部权限，可以配置公用模型、积分、用户、系统设置和审计导出。
- `admin`：普通管理员。可以查看运营数据、查看记录、处理普通用户，但不能操作主管理员，也不能修改核心系统配置。
- `operator`：运营人员。可以查看运营驾驶舱、创作记录、模型健康和用户基础信息，不能删除、扣分或修改密钥。
- `viewer`：只读人员。只能查看图表和列表，不能执行写操作。

当前数据库没有角色表时，第一阶段可用配置和后端函数映射：

- 配置中的管理员邮箱默认为 `super_admin`。
- 后续新增 `admin_roles` 或 `user_permissions` 表时，不影响现有 `is_admin_user`。
- `require_admin_user` 继续作为总入口，细粒度权限在具体接口内二次校验。

### 权限点

模型权限：

- `model:view`
- `model:create`
- `model:update`
- `model:delete`
- `model:publish`
- `model:unpublish`
- `model:test`
- `model:pricing`
- `model:secret:view_summary`

用户与积分权限：

- `user:view`
- `user:update`
- `user:disable`
- `user:delete`
- `user:restore`
- `user:role:update`
- `credit:view`
- `credit:adjust`
- `credit:settings`

记录与审计权限：

- `record:view`
- `record:raw_json`
- `record:export`
- `audit:view`
- `audit:export`

系统权限：

- `settings:view`
- `settings:update`
- `maintenance:user_merge`

### 危险操作约束

- 操作自己账号、删除管理员、禁用管理员、扣减管理员积分默认禁止。
- 发布/取消公用模型、删除模型、删除用户、扣减积分、修改注册送积分、用户合并都必须二次确认。
- 高风险操作必须写 `AdminOperationLog`，包含操作者、目标、动作、结果、摘要。
- 后台页面可以隐藏无权限按钮，但后端仍要返回 403。

## 精细图表与统计数据设计

运营数据以 `CallLog`、`CreditTransaction`、`ConversationMessage`、`GeneratedAsset`、`ModelGroup`、`User`、`AdminOperationLog` 为核心数据源。

### 驾驶舱图表

必须支持：

- 调用趋势：按日、周、月展示总调用、成功、失败、超时。
- 能力分布：文案、图片、视频调用占比。
- 模型分布：公用模型与私有模型调用占比。
- 积分趋势：预扣、确认消费、退款、管理员调整。
- 失败模型排行：失败次数、失败率、最近错误、最近失败时间。
- 慢模型排行：平均耗时、P95 耗时、超时率。
- 活跃用户排行：调用次数、公用模型次数、私有模型次数、积分消耗。
- 队列与轮询：平均队列时间、平均轮询次数、处理中任务数。

### 记录页统计

文案记录：

- 提问关键词、回答关键词、状态、模型、用户、耗时。
- Markdown 渲染开关和 raw JSON 展开。

图片记录：

- 图片尺寸、比例、质量、参考图数量、结果图数量、是否异步任务、是否退款。
- 瀑布流和列表两种视图。

视频记录：

- 视频模式、时长、分辨率、比例、参考图数量、任务状态、任务 ID、播放地址、轮询时间线。

### 新增或增强接口建议

保留现有接口，同时新增更适合后台图表的聚合接口：

- `GET /api/admin/dashboard/metrics?range=7d|30d|90d`
- `GET /api/admin/dashboard/trends?period=day|week|month`
- `GET /api/admin/dashboard/model-health`
- `GET /api/admin/dashboard/user-activity`
- `GET /api/admin/records?capability=text|image|video|all`
- `GET /api/admin/records/{message_id}`
- `GET /api/admin/tasks/{task_id}/timeline`
- `GET /api/admin/users/{user_id}/activity`
- `GET /api/admin/models/{model_id}/health`
- `GET /api/admin/permissions/me`

如果第一阶段不新增表，也可以从现有表聚合；但接口返回结构要稳定，便于后台图表和筛选持续迭代。

## 菜单结构

### 1. 运营驾驶舱

展示系统运行和业务概览：

- 今日/本周/本月调用量。
- 文案、图片、视频调用趋势。
- 成功率、失败率、超时率。
- 积分消耗、充值、退款数据。
- 公用模型调用占比和私有模型调用占比。
- 失败模型排行，点击可跳转到对应创作记录筛选。
- 近期高风险操作摘要。

接口：

- `GET /api/admin/overview`
- `GET /api/admin/overview/users`
- `GET /api/admin/overview/models`
- `GET /api/admin/credits/transactions`
- `GET /api/admin/audit-logs`

### 2. 模型中心

管理公用模型、私有模型可见性和模型成本：

- 按文案、图片、视频分类筛选。
- 搜索模型名称、供应商、Base URL、模型名。
- 展示模型状态、公用状态、拥有者、调用成功率、失败数、最近调用。
- 批量测试模型。
- 批量公用、批量取消公用。
- 测试后移除不可用模型，删除前二次确认。
- 设置公用展示名、描述、图标、默认参数。
- 设置文案/图片/视频积分扣除额度。
- 图标预览和加载失败提示。

接口：

- `GET /api/admin/models`
- `PUT /api/admin/models/{model_id}`
- `PUT /api/admin/models/{model_id}/credit-pricing`
- `POST /api/admin/models/{model_id}/publish`
- `POST /api/admin/models/{model_id}/unpublish`
- 需要补齐批量操作接口，或前端串行调用单模型接口。

### 3. 提示词中心

管理 AI 完善提示词能力：

- 文案、图片、视频三类模板。
- 模型级启用/禁用。
- 模板内容编辑。
- 模板版本历史。
- 多样例测试，展示原始输入和优化后结果。
- 总览每个模型是否启用提示词优化。

接口：

- `GET /api/admin/prompt-templates`
- `PUT /api/admin/prompt-templates/{template_id}`
- `POST /api/admin/prompt-templates/test`

### 4. 用户与积分

管理用户账号和积分：

- 用户列表：邮箱、昵称、手机号、状态、管理员标记、积分余额、注册时间、最近登录。
- 搜索用户邮箱、昵称、手机号。
- 角色筛选：管理员、普通用户。
- 状态筛选：正常、禁用、删除。
- 用户详情抽屉：基础资料、积分账户、积分流水、最近创作、最近登录 IP。
- 启用、禁用、删除、恢复用户。
- 管理员变更需要二次确认。
- 给用户充值或扣减积分，必须记录原因。
- 导出用户列表和积分流水。

接口：

- `GET /api/admin/users`
- `PUT /api/admin/users/{user_id}`
- `GET /api/admin/users/{user_id}/credits`
- `POST /api/admin/users/{user_id}/credits/adjust`
- `POST /api/admin/users/{user_id}/disable`
- `POST /api/admin/users/{user_id}/enable`
- `POST /api/admin/users/{user_id}/delete`
- `POST /api/admin/users/{user_id}/restore`
- `GET /api/admin/credits/settings`
- `PUT /api/admin/credits/settings`
- `GET /api/admin/credits/transactions`

### 5. 创作记录

统一管理文案、图片、视频记录：

- 顶部类型切换：全部、文案、图片、视频。
- 用户模糊筛选。
- 模型筛选。
- 时间范围筛选。
- 状态筛选：成功、失败、处理中、超时。
- 文案记录：默认展示提问和回答，JSON 默认收起。
- 图片记录：展示提示词、参考图缩略图、结果图缩略图；支持瀑布流视图和列表视图。
- 视频记录：展示提示词、任务 ID、状态时间线、在线播放、复制任务 ID。
- 详情抽屉展示完整请求、响应、资产、错误归因。

接口：

- `GET /api/admin/records/text`
- `GET /api/admin/records/images`
- `GET /api/admin/records/videos`

### 6. 审计日志

展示后台操作记录：

- 按管理员、目标对象、动作、风险等级、时间筛选。
- 删除、禁用、扣减积分、取消公用等标记为高风险。
- 查看操作前后摘要。
- 导出审计日志。

接口：

- `GET /api/admin/audit-logs`

### 7. 系统设置

集中配置站点基础能力：

- 站点名称、Logo、favicon。
- 默认主题。
- 注册是否开放。
- 新用户注册送积分数量。
- 任务轮询间隔和超时时间建议值。
- 上传限制、图片预览限制。
- 公用模型默认展示策略。

已有接口不足时，新增 `/api/admin/settings` 类接口，后台只做管理入口，不把系统配置写死在前端。

## 前端工程分层

`admin/` 建议结构：

```text
admin/src
├─ api/          认证、模型、用户、积分、记录、审计 API
├─ layouts/      AdminLayout、菜单、顶部栏
├─ router/       路由和管理员守卫
├─ stores/       auth、theme、app
├─ views/        dashboard、models、prompts、users、records、audit、settings
├─ components/   搜索栏、数据表格、详情抽屉、确认弹窗、状态标签
└─ styles/       tokens、theme、element-plus override
```

后台 API 层需要统一处理：

- `credentials: include`。
- CSRF 自动附加和失效重试。
- 401 跳登录。
- 403 展示无权限。
- 后端系统级错误转换为用户可读文案。

## 从旧后台迁移

要从 `fronted` 删除：

- `#/admin` 路由入口。
- `shell-admin` 相关页面结构。
- 旧后台状态、筛选、抽屉、记录视图逻辑。
- 旧后台 CSS 覆盖层。
- 旧后台测试用例。

要保留在 `fronted`：

- 用户设置页。
- 个人中心。
- 模型配置里普通用户可用的能力。
- 创作主站的登录、授权登录、历史记录和主题切换。
- 所有用户侧 API 封装。

删除旧后台时要避免误删：

- 公用模型在主站展示和使用逻辑。
- 普通用户不能编辑公用模型的限制。
- 积分展示和扣费提示。
- 创作记录保存和轮询逻辑。
